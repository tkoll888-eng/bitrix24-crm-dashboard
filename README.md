# CRM-дашборд по сделкам (Битрикс24 Вайбкод)

Встраиваемое приложение-дашборд для портала Битрикс24, которое показывает
аналитику по сделкам CRM текущего пользователя/портала.

---

## Назначение и реализованные сценарии

Приложение открывается внутри Битрикс24 (по прямой ссылке или как пункт левого
меню) и работает от лица авторизованного пользователя. Оно читает реальные данные
CRM портала через REST-прокси Вайбкода (на стороне сервера, ключ в браузер не
попадает) и показывает три блока аналитики:

1. **Ключевые показатели (KPI):**
   - общая сумма всех открытых (в работе) сделок портала;
   - количество выигранных сделок за выбранный период и их сумма;
   - средний чек (по выигранным сделкам за период).
2. **Сводка по стадиям воронки:** количество сделок и их сумма по каждой стадии
   (`stageId`) с визуальным распределением по объёму суммы; подписи стадий
   резолвятся из справочника статусов CRM.
3. **Последние сделки:** список 10–20 последних сделок с названием, суммой,
   стадией и ответственным (имя ответственного резолвится через справочник
   пользователей).

Дополнительно реализован **фильтр по периоду создания сделки**: готовые пресеты
(30/90/180 дней, год, всё время) и произвольный диапазон «с — по» с корректной
обработкой выбора (даты отправляются на сервер и применяются как фильтр
`createdAt` во всех запросах, включая агрегаты).

Воронка и показатели считаются **серверными агрегатами** (`/<entity>/aggregate`),
а не пересчётом одной страницы данных — это единственный честный источник
цифр для дашборда. Сервер проверяет флаг `meta.truncated` у агрегатов и честно
предупреждает пользователя, если период настолько широк, что портал обработал
лишь часть данных.

## Используемые данные и эндпоинты

- `POST /deals/aggregate` — сводка по стадиям (groupBy `stageId`, sum+count),
  сумма открытых (filter `stageSemanticId:"P"`), выигранные за период
  (filter `stageSemanticId:"S"` + `closeDate` в окне).
- `POST /deals/search` — последние сделки (sort `id desc`, select узкого набора
  полей).
- `POST /statuses/search` — справочник стадий воронки для подписей.
- `POST /users/search` — справочник ответственных для имён.
- `GET /me` (инфраструктурный) — проверка подключения ключа.

## Запрошенные скоупы и их обоснование

Работа приложения строится на реальном REST-доступе к порталу пользователя
через прокси Вайбкода. Приложение только **читает** CRM — ничего не создаёт, не
меняет и не удаляет, поэтому запрашиваются только права на чтение:

- **`crm` (deals)** — чтение сделок (`/deals/search`, `/deals/aggregate`) для
  всех трёх блоков дашборда. Без него приложение не имеет смысла.
- **`crm` (statuses)** — справочник стадий воронки (`/statuses/search`) для
  преобразования кодов `stageId` в человекочитаемые названия.
- **`user`** — справочник пользователей (`/users/search`), чтобы показать имя
  ответственного по сделке. **Опционально**: без него приложение работает, но
  имя ответственного не показывается (см. ограничения).

## Известные ограничения

- **Данные показываются по правам пользователя**: пользователь видит только те
  сделки, к которым у него есть доступ в Битрикс24 (права применяются на стороне
  портала). Это не баг, а штатное поведение.
- **Отсутствие скоупа `user`** у ключа: если у подключённого ключа нет доступа
  к `/users/search` (403 SCOPE_DENIED), имена ответственных в блоке «Сделки»
  показываются как «—». Остальные блоки дашборда работают в полном объёме.
- **Агрегаты по очень широким периодам** (например, «всё время» на портале с
  сотнями тысяч сделок) могут не досчитаться на стороне портала. Обрабатывается:
  сервер видит `meta.truncated` и честно сообщает «сузьте период».
- Выигранные сделки за период считаются по **дате закрытия** (`closeDate`), а
  фильтр периода в дашборде — по **дате создания** (`createdAt`). Это осознанный
  выбор: ключевые показатели не завязаны на фильтр окна.
- Суммы отображаются в рублях; мультивалютные сделки приводятся к их собственной
  валюте с отображением числового значения (валютная конвертация не выполняется).
- Ключ портала не хардкодится: читается из `process.env` (`BITRIX_API_KEY`,
  `BITRIX_API_BASE_URL`, `BITRIX_PORTAL_DOMAIN`). В репозиторий/архив ключ не
  попадает; без ключа сервер стартует и отвечает на `/api/*` понятной ошибкой,
  а интерфейс показывает состояние «портал не подключён».

## Инструкция для проверяющего

1. Убедиться, что в проекте есть `package.json` со скриптом `start`, и локально
   выполнить `npm install` (зависимостей нет — проходит мгновенно), затем
   `npm start`.
2. Открыть приложение по ссылке `https://app-<id>.vibecode.bitrix24.tech`
   во встроенном браузере Коворка (там есть сессия портала) — либо добавить его
   как пункт левого меню Битрикс24.
3. Проверить три сценария:
   - вкладка **Обзор** — карточки KPI, воронка по стадиям, список последних сделок;
   - вкладка **Воронка** — сводка по стадиям с количеством и суммами;
   - вкладка **Сделки** — таблица последних сделок (название, сумма, стадия,
     ответственный, дата).
4. Поменять **период** (пресет или произвольный диапазон) и нажать «Применить» —
   все блоки должны пересчитаться с учётом нового периода.
5. Если ключ портала не привязан — убедиться, что интерфейс показывает состояние
   «портал не подключён», а не падает.

## Placement deployment and local development

Embedded production uses `BITRIX_APP_KEY`. The gateway forwards the authenticated
placement session from `X-Vibe-Authorization` to the upstream `Authorization`
header; the browser never receives either credential. CRM caches use per-session cache isolation, so data derived for one placement session is never reused for another session.

`BITRIX_API_KEY` is a local-only fallback for development. It is used only when
`BITRIX_ALLOW_PERSONAL_FALLBACK=true` is explicitly set. Production must not deploy BITRIX_API_KEY or .env.
Deploy only the app key and ordinary non-secret runtime configuration. The existing placement is `LEFT_MENU`, and deployment reuses the existing server rather than creating a second server.

When the personal fallback is enabled, the development server binds only to
`127.0.0.1`. Production keeps the platform listener behavior and never enables
that fallback. CRM-derived caches are isolated per session, expire by TTL, and
use bounded LRU eviction so distinct sessions and date ranges cannot grow memory
without limit.
